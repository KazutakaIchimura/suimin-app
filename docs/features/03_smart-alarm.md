# スマートアラーム

## 1. 概要
- 睡眠サイクルの区切り（眠りが浅くなる時刻）に合わせて起こすアラーム。2つの使い方を1つの画面（`/alarm`）で提供する
  - **今から寝る**：今から寝た場合の、4・5・6サイクル目の区切りの3つの時刻を候補に出す
  - **起床時刻を指定**：就寝予定時刻（既定は今）と起床したい時刻（希望時刻）を入れると、希望時刻より前の区切りを遅い順に最大2つと、希望時刻そのものを候補に出す（区切りが希望時刻と同じ分ならまとめる。3.1）。希望時刻より遅くは鳴らさない
- 候補を押すと、その時刻に OS のアラーム（iOS は AlarmKit、Android は `AlarmManager.setAlarmClock`）を予約する。アラームは同時に1つだけで、新しく設定すると前のものを置き換える
- 鳴ったアラームは「停止」と「スヌーズ」（9分後にもう一度鳴る）で止める
- 入眠時間とサイクル長は、最初は標準値（入眠14分・1サイクル90分）を使い、01 で貯めたステージのある主睡眠から、直近30日にその値を求められる日が14日以上あれば、本人の実績の中央値に切り替える（入眠時間とサイクル長は別々に切り替わる。3.1）
- 一覧画面の上に、アラームの画面への入口と、設定中のアラームの時刻を出す
- 次のことは、2026-11-28 に人間が選択肢から選んで決めた：スヌーズ（停止とスヌーズで止める）、起床時刻を指定の候補に希望時刻そのものを入れること、一覧の入口に設定中のアラームの時刻を出すこと。前の2つと iOS 26 以上は、この機能のブランチで `docs/requirement.md` に書き足した（人間の判断）

## 3. 詳細設計

### 3.1 用語と業務ルール

| 用語 | 定義 |
| --- | --- |
| 入眠時間 | 寝始めてから眠るまでの分 |
| サイクル長 | 睡眠サイクル1回の分 |
| 区切り | 寝始めた時刻＋入眠時間＋サイクル長×n（n は1以上の整数。n サイクル目の区切り）。眠りが浅くなり、起きやすい時刻とみなす |
| 使う値 | 区切りの計算に使う入眠時間・サイクル長。それぞれ、実績（推定値）か標準値のどちらか |
| 標準値 | 入眠 14分・サイクル 90分（要件の値） |
| 候補 | アラームを鳴らす時刻の選択肢。分単位（秒以下は切り捨て） |

#### 入眠時間とサイクル長の推定（純粋関数）
- 元データ：帰属日が「今日の29日前」〜「今日」（30日分。今日は端末の現在日。02 の `localDate`）の**主睡眠**（01 の定義）のうち、ステージありのもの（01 の `hasStages`）。01 の読み取りの窓口に足す関数で読む（3.3）
- その日の入眠時間：主睡眠の就寝から、最初の「覚醒以外のステージ区間（`light`・`deep`・`rem`・`unspecified`）」の開始までの分（切り捨て）
  - 切り捨てる前の長さが60分以下（3,600,000ミリ秒以下）の日だけ使う。60分より長い日は、寝る前のスマホ・夜中の記録の誤りなどの外れ値として使わない（境目：60分0秒ちょうどは使う、60分0.001秒・60分59秒は使わない）
  - 覚醒以外のステージ区間が1つもない日（ステージありでも、DB の値の組み合わせとしてありうる）は、その日の入眠時間はない
  - 「最初」はステージ区間の開始が最も早いもの（受け取る順番には頼らない）
  - ステージ区間が就寝より前に始まることはない（01 の就寝は、含まれるセグメントの開始の最小値。01 の 3.1）ので、入眠時間は負にならない
  - 計測した機器が眠ってから記録を始める場合（深い・浅い睡眠から始まる）は 0分になる。その日も使う
- その日のサイクル長：レム睡眠のまとまり（以下「レム期」）の終わりの間隔
  1. `rem` のステージ区間を開始の順に並べ、前のレム期の終わりから次の `rem` 区間の開始までの空きが **30分未満**なら同じレム期につなぐ（短い覚醒などで分かれたレムを1つに数える。30分ちょうどは別のレム期）
  2. 隣り合うレム期の終わりどうしの間隔（分、切り捨て）を求める
  3. 60分以上150分以下の間隔だけを残す（境目はどちらも含む）。残った間隔の中央値（下の「中央値」）を、その日のサイクル長とする。残った間隔が1つもなければ、その日のサイクル長はない
- 使う値の決め方（入眠時間とサイクル長は別々に決める）
  - その日の値がある日が **14日以上**なら、それらの中央値を実績として使う
  - 13日以下なら標準値を使う
  - そのため「入眠は実績・サイクルは標準値」の組み合わせもありうる
- 中央値：値を小さい順に並べた真ん中。個数が偶数なら真ん中の2つの平均を `Math.round` で分に四捨五入する（02 と同じ。.5 は大きいほうへ）
- 画面には、使う値と、実績か標準値かを出す（3.4）。標準値のときは、切り替えまでに足りない日数（14 − 値のある日数）も出す

#### 候補の計算（純粋関数）
- 区切りの時刻は、基準の時刻（UNIX ミリ秒）に「入眠時間＋サイクル長×n」の分を足し、秒以下を切り捨てる
- 今から寝る
  - 基準は今（描画のたびに `@/lib/clock` から取る）
  - n＝4・5・6 の区切りの3つを、早い順に出す
- 起床時刻を指定
  - 就寝予定時刻・希望時刻は時と分だけを入れる（日付は入れない）。日付は次のように決める
    - 就寝予定時刻：今（分に切り捨て）以降で最も近い、その時と分の時刻。今と同じ時と分なら、今の分（例：今 22:30:40 に 22:30 → 今日の 22:30、22:00 → 翌日の 22:00）
    - 希望時刻：就寝予定時刻より後で最も近い、その時と分の時刻（就寝予定時刻と同じ時と分なら24時間後）
  - 就寝予定時刻の既定は今（分に切り捨て）。画面を開いているあいだに時刻が進んでも、利用者が変えていなければ「今」に追従する（描画のたびに今を取る）
  - 利用者が就寝予定時刻を選んだら、選んだときに上の決め方で日付まで決めた時刻（UNIX ミリ秒）を持つ。その時刻が今（分に切り捨て）より前になったら（例：22:00 を選んで 22:01 になった）、選んだ時刻を捨てて「今」の追従に戻す（翌日にずらさない。2026-11-28 に人間が判断）。ちょうど同じ分のあいだは選んだ時刻のまま
  - 希望時刻の既定は 7:00
  - 候補は、希望時刻そのものと、希望時刻**より前**の区切りのうち遅い順に最大2つ。早い順に並べて出す（例：標準値で就寝予定 22:30、希望 7:00 → 区切りは 0:14・1:44・3:14・4:44・6:14 なので、候補は 4:44・6:14・7:00）
    - 区切りが希望時刻とちょうど同じ分になったら、その区切りは希望時刻と同じものとして1つにまとめ（「希望の時刻」として出す）、それより前の区切りから最大2つを出す
    - 希望時刻より前の区切りが1つもない（睡眠が短い）ときは、希望時刻だけを出す
    - 区切りは n＝1 から数える（1サイクル目もありうる）
- 各候補に、睡眠の長さの目安として「基準（今／就寝予定時刻）から候補までの時間」を付ける（3.4）

#### アラームの設定
- 候補を押すと、次の順で設定する
  1. アラームの許可を確かめ、なければ求める（下の「許可」）。許可がなければ設定せず、案内を出す
  2. 押した時刻が今以前なら（候補を出してから時間が経った・許可の確認に時間がかかった）、設定せず「その時刻は過ぎています」を出す。比べるのは秒の切り捨て後の候補の時刻（UNIX ミリ秒）と今の時刻（ミリ秒まで）。ちょうど同じは「今以前」、1ミリ秒でも後なら設定する（例：候補 6:58:00 に今 6:58:30 → 過ぎている）。この「今」は許可の要求が終わったあとに取る（窓口は今を取る関数 `getNow` を受け取る。01 の同期と同じ形）
  3. 押した時刻に1回だけ鳴るアラームを予約する（ID は UUID v4。iOS は UUID でなければならないため）
  4. 予約に成功したら、新しい ID 以外のこのアプリのアラームをすべて取り消す（同時に1つだけにするため。先に予約するので、置き換えの途中でアラームが1つもない時間ができない）。取り消すアラームの集め方は「解除」と同じ。集めるための読み取り（予約の一覧・予定）が失敗したときも、取り消しの失敗と同じに扱う（下の「前のアラームを取り消せませんでした」）
- 設定に成功したら「6:58 にアラームを設定しました」を出す
- 許可の要求・予約が失敗したら（例外）「アラームを設定できませんでした」を出す（前のアラームは残る）
- 予約に成功したあとの取り消しが失敗したら（例外）「6:58 にアラームを設定しましたが、前のアラームを取り消せませんでした」を出す（新しいアラームは残り、前のアラームも残ることがある）
- 成功・失敗にかかわらず、設定のあとは「設定中のアラーム」を読み直す（予約のあとの取り消しが途中で失敗すると、新旧の2つが残ることがあるため。そのときは画面に実際の状態（最も早いもの）が出て、失敗の文言で利用者が気づける）
- 鳴らし方（ライブラリの予約の設定。ライブラリの値はリポジトリ層の1か所に置く）
  - 題名「起床の時間です」、音は OS の既定、振動あり（Android）
  - ボタン：「停止」と「スヌーズ」。スヌーズのボタンは「アプリを開く」ボタン（`secondaryButtonBehavior: 'openApp'`）にし、アプリが開いたら下の「スヌーズ」のとおり次の鳴動を予約する（ライブラリにスヌーズ専用のボタンがないため。2026-11-28 に人間が了承）
  - 止め方は既定（`alertActionMode: 'default'`。停止のボタンで止まる）。アプリを開かないと止まらない設定は使わない
  - 停止を押したときは記録だけ（`stopIntentBehavior: 'recordOnly'`）
  - Android：誰も止めなければ **5分**で鳴り止む（`maxRingDurationSeconds: 300`。人間が判断）。スヌーズを押したときに開くアプリのリンク（`launchUri`）は指定しない（アプリは最初の画面で開き、アラームの画面への移動はスヌーズのフックだけが行う。リンクでも移ると、`/alarm` が2回積まれたり、冷えた起動で `/alarm` だけになり戻る先がなくなったりするため）
  - スヌーズ中の iOS の表示（`countdownTitle`）は「スヌーズ中」

#### 許可
- 設定のたびに、ライブラリの許可の要求（`requestPermissionsAsync`）を呼ぶ（まだ決めていなければ OS の確認が出る。決めてあれば今の状態を返す）
- 結果から案内を決める（純粋関数）

| 結果 | 設定するか | 案内 |
| --- | --- | --- |
| `status` が `unavailable` | しない | 「この端末ではアラームを使えません」 |
| `status` が `denied`・`notDetermined`・`unknown`、または `canScheduleExactAlarms` が偽 | しない | 「アラームの許可がありません。設定で許可してください」と「設定を開く」（`openAlarmSettingsAsync`）。`canOpenSettings` が偽ならボタンを出さない |
| 上以外で `canUseFullScreenIntent` が偽（Android 14 以降。省略（`undefined`）は真とみなす） | する | 設定の成功の表示に加えて「ロック中の画面にアラームを大きく出すには、設定で許可してください」と「設定を開く」（`openFullScreenIntentSettingsAsync`）。許可がなくても音は鳴る（ライブラリの説明） |
| 上以外 | する | なし |

- 許可の結果の値のうち、`status`・`canScheduleExactAlarms`・`canOpenSettings` はライブラリの型で必ずある（省略できない）。`canUseFullScreenIntent`・`canPostNotifications` は省略できる（ライブラリの型の説明：Android 以外では常に真）ので、省略は真とみなす
- 「設定を開く」が失敗したら（例外・偽を返す）「設定を開けませんでした」を出す。どちらも `smartAlarm.openSettings` の error ログを出す（例外は `err`、偽は `err` の代わりに `opened: false`）。例外はログのあと投げ直し、受け口層が文言にする
- Android の正確なアラームの権限は、目覚ましのアプリなので `USE_EXACT_ALARM`（インストール時に与えられる）を設定プラグインで有効にする。`SCHEDULE_EXACT_ALARM` も残す（ライブラリの既定）。それでも許可がない（利用者が取り消した）ときは上の表のとおり案内する
- 通知の許可（Android 13 以降の `canPostNotifications`）は案内に使わない（鳴動は常駐サービスと全画面表示で行い、通知の許可がなくても鳴る（ライブラリの説明）。実機で確かめる。3.6）

#### 設定中のアラーム
- ライブラリの鳴動の予定（`getAlarmOccurrencesAsync`）のうち、`phase` が `scheduled` で最も早いものを「設定中のアラーム」とする。スヌーズで予約した次の鳴動（`relationship` が `deferred`）も同じに扱い、「スヌーズ」と分かるように出す（3.4）
- `scheduled` の予定がなければ「未設定」
- 読み直すのは、アラームの画面・一覧の入口を開いたとき、アプリが前面に戻ったとき（`background` → `active`。01 と同じ条件）、設定・解除・スヌーズのあと
- 読み取りに失敗したら「アラームの状態を読み込めませんでした」と「再試行」を出す
- 読み直しが重なったとき（例：前面復帰の読み直しが、設定の直後の読み直しより後に終わる）は、**最後に始めた読み直しの結果だけ**を使う（store が読み直しの番号を持ち、終わったときに最新の番号でなければ捨てる）。古い結果で新しい状態を上書きしないため

#### 解除
- 「解除」を押すと、このアプリのアラームをすべて取り消す（予約の一覧 `getScheduledAlarmsAsync` の全 ID と、`scheduled` の予定の `alarmId` に `cancelAlarmAsync`。スヌーズの予定が予約の一覧に出るかがドキュメントにないため、両方から集める）
  - 集めた ID は重なりを除き、同じ ID には1回だけ呼ぶ
  - 0件なら何も呼ばず成功とする（「アラームを解除しました」）
  - 1件ずつ順に呼び、途中で失敗したら残りは呼ばずに失敗とする（取り消せたものは戻さない）
  - ID を集める読み取り（予約の一覧・予定）が失敗したら、何も取り消さずに失敗とする
- 解除に成功したら「アラームを解除しました」、失敗したら「アラームを解除できませんでした」を出す。成功・失敗にかかわらず「設定中のアラーム」を読み直す（途中で失敗したときに、残った実際の状態を出すため）

#### スヌーズ
- アプリの起動時と前面に戻ったとき（`background` → `active`）に、ライブラリの「アプリを開いた理由」（`getPendingNativeAlarmHandoffAsync`）を読む（ライブラリの説明：イベントはアプリが動いていないと届かないので、起動と前面復帰のたびに読む）
- 理由の読み取りが失敗したら（例外）、`smartAlarm.snooze` の error ログを出し、画面は移らず、何も表示しない（スヌーズかどうか分からないため）。次の前面復帰でまた読む
- 古い理由は捨てる：理由の `timestamp`（押した時刻）が今より **10分**以上前なら、スヌーズせずに理由を消す（鳴動が終わったあとの、関係のない時刻にスヌーズしないため。Android の鳴動は5分で止まり、iOS でも押してから10分たってアプリを開くのはスヌーズの意図ではないとみなす。境目：9分59.999秒前は処理する、10分ちょうど前は捨てる）。今より後の時刻（端末の時計のずれ）は新しい理由として処理する
- 理由の `action` が `secondaryOpen`（スヌーズのボタン）なら
  1. 鳴っている鳴動の ID を、`getCurrentAlarmContextAsync` の `occurrenceId` から取る。取れなければ、鳴動の予定（`getAlarmOccurrencesAsync(理由の alarmId)`）のうち `phase` が `ringing` のものの `occurrenceId`。`getCurrentAlarmContextAsync` が例外を投げたら予定に回さず失敗とする（ライブラリが使えない状態なので）。どちらでも取れなければ失敗とする（理由の型には鳴動の ID がないため。アラームの ID に戻すと、2回目以降のスヌーズで `idempotencyKey` が前回と同じになり、次の鳴動が予約されないおそれがある）
  2. その鳴動を「延期」で終わらせ、**9分後**（540秒）に次の鳴動を予約する（`resolveAlarmOccurrenceAsync`、`outcome: 'deferred'`、`next: { delaySeconds: 540, relationship: 'deferred' }`）。同じ鳴動で二重に予約しないように `idempotencyKey` に `snooze:<鳴動の ID>` を渡す
  3. 成功したら理由を消し（`clearPendingNativeAlarmHandoffAsync`）、アラームの画面へ移って「7:07 にもう一度鳴ります」を出す（時刻は結果の `nextOccurrence.scheduledFor`）。結果の `status` が `resolvedWithoutNext` なら、理由を消したうえで「スヌーズを設定できませんでした」を出す（再試行は出さない。鳴動は終わっていて、やり直しても次の鳴動はできないため）
  - 再試行（下の 4）を押したときに理由が10分以上前になっていたら、理由を消し、出ていた「スヌーズを設定できませんでした」と「再試行」も消す
  4. 失敗したら（例外・鳴動の ID が取れない）理由を消さず、アラームの画面へ移って「スヌーズを設定できませんでした」と「再試行」（理由の読み取りからやり直す）を出す。理由を残すので、次の前面復帰でもやり直す（上の「古い理由は捨てる」により、10分たてば捨てて失敗の表示も出さない）
- 理由の `action` がそれ以外（停止・Android で鳴り始めたときの記録など）なら、何もせずに理由を消す
- 理由の消去は、スヌーズとは別の窓口の関数（`clearHandoff`）にする。消去が失敗したら（例外）、窓口は `smartAlarm.snooze` の error ログを出して投げる（logging.md ルール3）。store（受け口層）は、スヌーズが成功していれば消去の失敗を受け取ってもスヌーズの結果（「7:07 にもう一度鳴ります」）をそのまま出す（スヌーズは成功しているため）。スヌーズ以外の理由の消去の失敗は、store が受け取って何も表示しない。理由が残るので次の前面復帰でまた処理するが、同じ鳴動には `idempotencyKey` で最初の結果が返り、二重に予約されない（ライブラリの説明）
- アラームの画面への移動は `router.navigate('/alarm')`（すでに `/alarm` を出していれば積み増さない）。冷えた起動でも最初の画面（一覧）の上に積まれるので、戻ると一覧になる
- スヌーズを何度押しても、そのたびに9分後に鳴る（鳴動ごとに ID が変わる。ライブラリの説明）
- 実機で確かめること（ドキュメントに書かれていない）：スヌーズのボタンでアプリが開くあいだに音が鳴り続けるか（iOS）、スヌーズのあとに最初の鳴動が止まるか（3.6）

#### 例外の扱い
- ライブラリの呼び出しの失敗は、サービス層がログを出して投げ直し（logging.md）、受け口層（store）が受け取って画面の文言にする（01 と同じ形）
- 推定の元データ（DB）の読み取りに失敗したら、標準値を使い、「睡眠の記録を読み込めなかったため、標準値を使っています」を出す（アラームは設定できるようにする）。失敗は 01 の窓口がログを出して投げ、受け口層（`use-smart-alarm.ts`）が受け取って、標準値と失敗の印にする（上と同じく受け口層で文言にする。サービス層では握りつぶさない。logging.md ルール3）
- 推定の元データを読むのは、アラームの画面を開いたときと、画面を開いたままアプリが前面に戻ったとき（`background` → `active`）だけ。01 の store の版番号（`dataVersion`）は使わない（01 の受け口層なので、他機能から参照できない。architecture.md「機能境界」）
  - そのため、画面を開いたまま 01 の同期で睡眠が増えても、次に開く・前面に戻るまでは前の値のまま。前面に戻ったときは 01 の同期と読み直しが同時に始まり、同期の結果が間に合わないことがある。推定は14日分以上の中央値で、一晩分で変わることはほとんどないので、この割り切りでよいとした（3ラウンド目の plan レビューを受けて決めた）
- 推定の 30日の範囲の「今日」は、読み直すときの今日。画面を開いたまま日付が変わっても、読み直すまでは前の日の範囲のまま（1日ずれても中央値はほとんど変わらないため。02 と同じ割り切り）

### 3.2 テーブル定義
- 新しいテーブルは作らない。アラームの予約・予定はライブラリが端末の中（ネイティブの保存先）に持ち、再起動後も残す（ライブラリの説明）。アプリの DB に写しを持つと、OS 側で鳴った・止めた・取り消したときにずれるため
- 01 のテーブルは読むだけ（01 の読み取りの窓口を通す。architecture.md「機能境界」）
- 標準値（14分・90分）・切り替えの日数（14日）・元データの日数（30日）・外れ値の境目・スヌーズの間隔（9分）・Android の鳴動の長さ（5分）は、設定テーブルに置かず `smart-alarm.types.ts` の定数にする。要件と人間の判断で決めた仕様の値で、利用者や運用で変える値（database.md の「値が変わる業務設定」）ではないため。変える設定はスコープ外（8）
