# create-pr(PR本文を構造化して投稿する)

## 0. 開始条件（AI相互レビューの合格確認）

- PR作成前に、`ai-review` スキル（段階：impl）が実施済みで合格していること
- 対象の設計書の「レビュー記録」節に impl 合格の行があり、それ以降に実装を変更していないこと
  - 確認方法：最新コミットが impl 合格のコミット（`ai-review` スキル手順6）であり、`git status --porcelain` が空であること
- 未実施、または P0・P1 が残っている場合は、PRを作らずに停止して報告する
- テストを全件（単体・中間・E2E）実行し、すべて通ること。あわせてビルド・リントも実行する
  - 1件でも失敗した場合は、PRを作らずに停止して報告する（skip・assert削除などで通さない）
  - 結果は手順2の「テスト」に書く

## 1. 差分と経緯を集める

- `git diff main...HEAD` で変更の全体を把握する
- 対応する設計書 (docs/features/) と、実装後のAIレビュー結果を読む

## 2. 本文を下書きする

次の見出しで、レビューアーが上から読めば理解できる順に書く。

- 課題: 何を解決するPRか (背景と、対応するissue・設計書)
- 解決策: どう変えたか。設計判断とトレードオフを1～2行で
- テスト: 追加・変更したテストと、手順0の全件実行の結果
- レビュー観点: とくに見てほしい箇所、影響範囲、未対応事項

下書きは docs/pr/ に保存し、投稿前に人間の承認を取る。
ファイル名は、対応する docs/features/ の設計書と同じ名前にする（例：`docs/features/01_login.md` → `docs/pr/01_login.md`）。
1つの機能を複数のPRに分ける場合は、2本目以降に枝番を付ける（例：`01_login.md` → `01_login_02.md` → `01_login_03.md`）。枝番も半角数字・ゼロ埋め2桁とする。
命名は .claude/rules/naming.md に従う。
下書きは `.gitignore` で除外しているため、コミットしない（`git add -f` で無理に追加しない）。

## 3. 投稿する

承認後、`gh pr create --body-file docs/pr/<ファイル名>` で下書きを本文として渡して作成する。CIの結果が出てから人間のレビューへ回す。
CI未設定のあいだは、手順0の全件実行の結果を本文の「テスト」に書いたうえで人間のレビューへ回す（本文に「CI未設定」と明記する）。
AI相互レビューは手順0で完了済みのため、PR作成後には行わない。
