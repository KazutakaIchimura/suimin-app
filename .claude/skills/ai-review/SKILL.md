# ai-review（段階別のAI相互レビュー）

## 0. 段階を決める

引数（`plan` / `test` / `impl`）で段階を決める。引数がなければ、差分の内容から判断し、判断できなければ確認する。

| 段階 | タイミング | レビュー対象 |
| --- | --- | --- |
| `plan` | 設計書（docs/features/）の作成・修正後、テストを書く前 | 設計書 |
| `test` | tdd スキルでテストリストを作成した後、テストコードを書く前。実装中にテストリストへ項目を追加したときも再実行する | 設計書の「テストリスト」節 |
| `impl` | 実装後、PR作成前（必須） | 実装・テストの差分すべて |

## 1. 段階ごとの観点と担当エージェント

### plan（設計書レビュー）
| 観点 | 担当エージェント |
| --- | --- |
| 要件との整合・8項目の網羅・異常系/境界値のテストケース漏れ・ルール（architecture.md・database.md・testing.md）との矛盾 | `plan-reviewer` |

### test（テストリストレビュー）
| 観点 | 担当エージェント |
| --- | --- |
| 設計書の「新規テストケース」との対応（不足・過剰）、境界値の両側・異常系・認可の抜け、単体/中間/E2Eの切り分け、期待結果の検証可能性 | `test-list-reviewer` |

### impl（実装レビュー）
| 観点 | 担当エージェント |
| --- | --- |
| 1. セキュリティー：認可漏れ、インジェクション、機密情報の露出 | `security-reviewer` |
| 2. テスト：変更に対するテストの有無・境界値・骨抜きテストの検出 | `edge-case-reviewer` |
| 3. 設計：1ファイル1責務・機能境界（architecture.md準拠） | `architecture-reviewer` |
| 4. ルール準拠：.claude/rules/ 配下の該当ルールとの矛盾 | `architecture-reviewer` |
| （補助）設計書との整合 | `design-reviewer` |

## 2. 実行方法

- `impl` のときは、起動前にメインセッションで `git add -N .` を1回だけ実行し、新規ファイルを差分に含める（レビュアーは `git diff` を読むだけにして、並列実行での `.git/index.lock` の衝突を防ぐ）
- 段階の担当エージェントを、すべてサブエージェントとして起動する。互いに依存しないので並列に起動してよい
- サブエージェントは実装の会話を引き継がない独立したコンテキストで動くため、これで「実装とは別セッションのAI」の条件を満たす。人間が別セッションを手で立てる必要はない
- 起動時の指示には、実装・設計の経緯・意図・言い訳を書かない。段階名と「対象をレビューせよ」、対象の設計書のパスだけを渡す
- 全エージェントの指摘を1つの一覧にまとめ、重複を除いてから P0/P1/P2 で判定する
- 再レビュー（P0・P1の修正後）も同じ段階・同じ手順で、担当エージェントすべてを起動し直す

## 3. 指摘事項の優先度分類

- **P0（必須修正）**：セキュリティー・データ破壊・機能の誤り（plan では要件との矛盾）。次の段階へ進めない
- **P1（必須修正）**：深刻なバグの芽、テスト網羅の欠落。スキップ不可。次の段階へ進めない
- **P2（軽微）**：スタイル、命名。時間があれば修正、なければTODO化

## 4. おわりの条件

- P0、P1がゼロなら合格。次の段階へ進んでよい（impl の合格後は create-pr へ進める）
- P2だけなら修正せず次へ進んでよい
- 3ラウンドを超えて指摘が循環したら、人間が決める

## 5. 結果を記録する

合格したら、対象の設計書の「## レビュー記録」節に1行で追記する（節は雛形に含まれている。古い設計書で節がなければ雛形の位置に作る）。
create-pr はこの記録で impl の合格を確認する。

```
- 2026-11-18 impl 合格（2ラウンド、P2: 1件 TODO化）
```

## 6. コミットする

記録を追記したら、その段階の成果物とレビュー記録をまとめて1コミットにする。main 上では実行せず、機能ブランチで行う（main にいたら停止して報告する）。

| 段階 | コミットに含めるもの | メッセージ例 |
| --- | --- | --- |
| `plan` | 設計書 | `01_login: 設計書 plan レビュー合格` |
| `test` | 設計書（テストリスト節・レビュー記録） | `01_login: テストリスト test レビュー合格` |
| `impl` | 実装・テスト・設計書（レビュー記録） | `01_login: 実装 impl レビュー合格` |

- メッセージの先頭は設計書のファイル名（拡張子なし）にする
- 合格前の途中状態はコミットしない
