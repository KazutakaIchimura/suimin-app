# 実装前の詳細設計書作成

## 作成方法
短い依頼から始めてAIに質問させて、技術面、エッジケース、トレードオフを聞きつくしたところで、仕様を１枚のファイルにまとめる

## 設計書の項目
設計書を作るときは、コードを書き始める前に、次の8項目をAIと対話しながらまとめる。この項目立ては開発に合わせて増減してよい。
1. 概要
- 何を作るか
2. 背景
- なぜ作るか、どの業務要件に対応するか
3. 詳細設計
- どのファイルをどう変えるか
- 変更対象のファイルはリポジトリ相対の実パスで書く（例：`src/features/sleep-record/...`）。
4. テスト影響範囲
- 既存のどのテストに影響するか
5. 新規テストケース
- 何をもって完成とするか（テストの一覧）
6. 実装順
- どの順に作るか（「失敗するテスト→最小実装」を部品ごとに並べたロードマップ）
7. コミット前テスト実行
- マージ前に何を走らせるか
8. スコープ外
- 今回やらないことは何か？

## 設計書の雛形
新規作成時は次の見出しをすべて最初から入れる。1〜8 は設計時に埋める。9〜11 は見出しだけ置き、本文は後の工程で追記する（設計時は空でよい）。

```markdown
# <機能名>

## 1. 概要
## 2. 背景
## 3. 詳細設計
## 4. テスト影響範囲
## 5. 新規テストケース
## 6. 実装順
## 7. コミット前テスト実行
## 8. スコープ外

## テストリスト
<!-- tdd スキル手順1で記入する。1項目に「種別（単体/中間/E2E）・前提・操作・期待結果・対応する新規テストケース」 -->

## レビュー記録
<!-- ai-review スキルが合格時に1行ずつ追記する（例：- 2026-11-18 plan 合格（1ラウンド）） -->

## 修正履歴
<!-- 既存機能の修正時に1行ずつ追記する（例：- 2026-12-01 ログイン失敗時のロック回数を5回に変更） -->
```

## 設計書作成後
- 作った設計書は、テスト・実装に入る前に `ai-review` スキル（段階：plan）でAI相互レビューにかける

## 新規機能の場合
- 最初に設計書の番号とファイル名を決める（ブランチ名に使うため、ブランチ作成より先に決める）
  - 番号は「使用済みの最大番号 + 1」とする。使用済みの番号は次の両方から集める
    - main の `docs/features/` にある設計書の番号
    - 未マージの機能ブランチの番号（`git fetch` のあと `git branch -a --list "*feature/*"` で確認する）。並行開発中の番号との重複を防ぐため
  - 作成順序が分かるように、番号は半角数字・ゼロ埋め2桁で振る（例：`01_login.md`。命名は .claude/rules/naming.md に従う）
- 設計書を作り始める前に、main から機能ブランチを作る（命名は .claude/rules/naming.md の「ブランチ名」に従う。例：`01_login.md` → `feature/01-login`）
- 作成した設計書は `docs/features/` に配置する

## 既存機能の修正の場合
- 修正に着手する前に、main から機能ブランチを作る（命名は新規機能と同じく対象の設計書名に合わせる）
- 修正に着手する前に、対象機能の設計書を `docs/features/` から探して読む
  - 探し方：① ファイル名（例：`01_login.md`）から機能名で探す ② 見つからなければ、変更するファイルのパス・機能名で `docs/features/` 内を全文検索する
  - 該当する設計書が見つからない、または複数見つかって判断できない場合は、推測で進めず作業を止めて報告する
- 既存機能の設計書を修正する
- 設計書の「## 修正履歴」節に、修正日・修正内容を端的にまとめ、１行で追記すること
