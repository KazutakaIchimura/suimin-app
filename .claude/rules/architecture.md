# architecture

## 構造 (どこに何を置くか)

```
src/
├── app/                                   # expo-router の画面ルート。features の画面コンポーネントを描画するだけ
│   ├── _layout.tsx                        # 全体のレイアウト・起動時の初期化（DBマイグレーションの適用など）
│   └── <画面>.tsx                          # 例：index.tsx, alarm.tsx
├── features/<機能名>/                     # ロジックの本体。機能単位で区切る（例：sleep-record, smart-alarm）
│   ├── <機能名>-screen.tsx                 # 受け口層：画面コンポーネント。表示と操作の受け付けだけ
│   ├── use-<機能名>.ts                     # 受け口層：画面用のフック。サービス層を呼び、結果を画面の状態にするだけ
│   ├── <機能名>.store.ts                   # 受け口層：画面をまたいで共有する状態（Zustand）。必要なときだけ作る
│   ├── <機能名>.service.ts                 # サービス層：ビジネスロジック（判定・計算・変換）
│   ├── <機能名>.repository.ts              # リポジトリ層：DB（Drizzle）・ヘルスケア・アラームの読み書き
│   ├── <機能名>.schema.ts                  # その機能が所有するテーブル定義（Drizzle）
│   └── <機能名>.types.ts                   # 型・データ定義
└── lib/                                   # 機能横断の共通処理のみ（ログ・DB接続・現在時刻の取得など）
```

- 各層は機能フォルダ内で別ファイルに分ける。1つの層が複数ファイルになるときは `<機能名>-<対象>.<層名>.ts` とする（例：`sleep-record-chart.service.ts`）
- ファイル名・フォルダ名はケバブケース（小文字と `-`）。命名は naming.md に従う
- 依存の向きは 受け口層（screen → hook / store）→ サービス層 → リポジトリ層 の一方向。逆向きの呼び出しをしない
- 画面コンポーネントからリポジトリ層・サービス層を直接呼ばない。フックを経由する
- `src/app/` のルートファイルに処理を書かない。features の画面コンポーネントを描画するだけにする
- サービス層・リポジトリ層は React に依存しない（`react` や `react-native` を import しない）
- iOS / Android で使うライブラリが違うもの（ヘルスケア）は、リポジトリ層の中で `Platform.OS` により切り替え、サービス層には同じ形のデータを返す

迷ったらこの順で問う:

1. 特定機能の業務ロジック → `src/features/<機能名>/`
2. どの機能にも属さない基盤 → `src/lib/`
3. 複数機能で共有したい処理 → 安易に共通化せず、まず各機能に置く

## 1ファイル1責務

- ファイルの担当を一文で言えること。「睡眠サイクルから起床時刻の候補を計算する」は合格、
  「睡眠まわりの処理いろいろ」は失格
- ファイルが肥大したら、責務の境界で割る

## 機能境界

- 他機能のテーブルへ直接クエリしない。所有機能のサービス層を経由する
  (例: スマートアラームが過去の睡眠実績を使うときは sleep-record のサービスを呼ぶ)
- 他機能から参照してよいのは、その機能のサービス層のファイルだけ。受け口層・リポジトリ層などのファイルは参照しない
  - 型・データ定義は、サービス層の関数の引数・戻り値に使うものに限り参照してよい
  - テーブル定義（`*.schema.ts`）は、DB接続（`src/lib/`）がスキーマを集めるためにだけ参照してよい
- 受け口層に業務ロジック・クエリを直書きしない。サービス層の関数を呼ぶだけにする
- 再エクスポートだけを行う集約ファイル（`index.ts` でのまとめ export）を作らない。実ファイルを直接 import する
  （依存関係が追えなくなり、循環参照の原因になるため）
- import は `@/` から始まるパス別名（`@/features/...`、`@/lib/...`）で書き、`../` で親フォルダをさかのぼらない

## 副作用の分離 (Functional Core / Imperative Shell)

- 業務判断・計算・変換は純粋関数に集める (Functional Core)
  - 例：睡眠サイクルの計算、睡眠実績からの入眠時間・サイクル長の推定、グラフ用の集計
- DBの読み書き・ヘルスケア・アラームの登録・現在時刻・乱数・環境変数参照は外側の薄い層へ寄せ、Coreが返した結果を説明するだけに近づける (Imperative Shell)
  - 現在時刻は業務ロジックの中で `new Date()` / `Date.now()` を呼ばず、引数で受け取る（テストで時刻を固定するため）
- 狙いは、複雑なロジックを外部依存なしでテストできる形に保つこと
