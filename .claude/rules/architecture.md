# architecture

> **【要編集】技術スタックが決まり次第、本ファイルを編集すること。**
> 現在は技術スタック未確定のため、言語・フレームワークに依存しない一般的な構成で記述している。
> スタック確定後、ファイル名・拡張子・層の対応（例：受け口をルーティングハンドラにするか等）を具体化する。

## 構造 (どこに何を置くか)

src/
├── features/<機能名>/   # ロジックの本体。機能単位で区切る
│   ├── 受け口層           # リクエスト・画面操作の入口。入力を受け取り、サービス層を呼んで結果を返すだけ
│   ├── サービス層         # ビジネスロジック（業務判断・計算・状態遷移）
│   ├── リポジトリ層       # データベース・永続化の読み書き
│   └── 型・データ定義     # その機能で使うデータ構造
└── lib/                   # 機能横断の共通処理のみ（ログ・設定読込など）

- 各層は機能フォルダ内で別ファイルに分ける。ファイル名は「<機能名> + 層名」が分かる形にする
  （具体的な命名・拡張子はスタック確定後に決める。命名は naming.md に従う）
- 依存の向きは 受け口層 → サービス層 → リポジトリ層 の一方向。逆向きの呼び出しをしない

迷ったらこの順で問う:

1. 特定機能の業務ロジック → `features/<機能名>/`
2. どの機能にも属さない基盤 → `lib/`
3. 複数機能で共有したい処理 → 安易に共通化せず、まず各機能に置く

## 1ファイル1責務

- ファイルの担当を一文で言えること。「請求書の金額計算」は合格、
  「請求書まわりの処理いろいろ」は失格
- ファイルが肥大したら、責務の境界で割る

## 機能境界

- 他機能のテーブルへ直接クエリしない。所有機能のサービス層を経由する
  (例: 入金処理がユーザー情報を更新するときは user のサービスを呼ぶ)
- 他機能から参照してよいのは、その機能のサービス層のファイルだけ。受け口層・リポジトリ層などのファイルは参照しない
  - 型・データ定義は、サービス層の関数の引数・戻り値に使うものに限り参照してよい
- 受け口層に業務ロジック・クエリを直書きしない。サービス層の関数を呼ぶだけにする
- 再エクスポートだけを行う集約ファイル（例：`index` ファイルでのまとめ export）を作らない。実ファイルを直接参照する
  （依存関係が追えなくなり、循環参照の原因になるため）

## 副作用の分離 (Functional Core / Imperative Shell)

- 業務判断・計算・変換は純粋関数に集める (Functional Core)
- DBの読み書き・外部API・時刻・乱数・環境変数参照は外側の薄い層へ寄せ、Coreが返した結果を説明するだけに近づける (Imperative Shell)
- 狙いは、複雑なロジックを外部依存なしでテストできる形に保つこと
